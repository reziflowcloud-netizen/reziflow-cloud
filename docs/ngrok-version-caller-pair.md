# Bounded Store ngrok caller-PATH diagnostic

Status: **prepared, not executed**. The actual relay failed at `CreateProcessW`, error 5, before assignment to a Job. A Windows policy denial has not been established. The earlier version fixture did not reproduce the relay environment: its PowerShell array expression produced one entry containing eight assignments. The corrected pure builder now produces eight independent entries. No inference of equivalent environments may rely on the old fixture.

The remaining hypothesis is that Store package activation needs its registered execution alias to be discoverable in the caller's PATH. The raw package image has package-identity-dependent execute access. Microsoft's [package execution discussion](https://github.com/microsoft/terminal/discussions/20060) and [WindowsAppSDK issue](https://github.com/microsoft/WindowsAppSDK/issues/4651) support investigation, but do not establish the cause on this computer. This diagnostic leaves the actual supervisor unchanged. It is a **surrogate version-only scenario**, not an exact replay: the old D-drive private environment has been deleted, and this probe uses a new C-drive empty scratch as both profile and working directory. The original `qa-source` contents and working-directory layout are not reproduced.

`node scripts/qa/meta-recovery/version-caller-pair.mjs --plan` is the default, offline plan: no child process, metadata verification, scratch directory, or ngrok call. `--metadata-only` additionally invokes only the pinned approved PowerShell host to validate the exact installed Store package, offline signature, manifest, image hash and known AppExecLink's family/application/image mapping. It never launches ngrok. Neither mode reads the QA pointer, runtime, database, credentials or provider configuration.

**Separate owner permission is required** for `--expected-owner-authorized-version-probe`. It prepares one empty ignored `.qa/ngrok-caller-pair-*` directory with access restricted to the owner, SYSTEM and Administrators, then performs at most two `ngrok version` calls. Both use the same raw image, approved Node parent, working directory, redirected profile/temp locations, exact eight-entry child environment, native flags and per-kind kill-on-close Jobs. Only the PowerShell caller's PATH differs: the actual guardian's minimal PATH, then that PATH plus the verified current-user WindowsApps alias directory. The alias itself is verified but is not the executable launched by either case.

The helper extracts only the pure environment-builder function from `supervisor-ngrok-version.test.ps1` and the pinned native C# literal from `supervisor-process.ps1`; it never executes either script's main entry point. A dummy Node peer occupies its own Job in each case. The parent, stdin EOF/STOP, shared 45-second deadline, per-child watchdog and kernel Job handles bound lifetime. If the guardian fails to acknowledge STOP within five seconds, Node terminates only its retained spawned child handle, then waits two seconds for exit; missing acknowledgement is reported as uncertain cleanup and blocks further cases. Both Jobs must stop with zero active processes; scratch must remain empty before continuing. No arbitrary executable/argument/config option, tunnel command, HTTP listener, DB operation, credential input, privilege change, breakaway flag or policy override exists in this probe. Child output is discarded; only bounded status, case, native operation/code and cleanup counts are returned.

Only successful cleanup permits the second case. The first case may continue after a clean `create_process` error 5; other unexpected failures stop. Error 5 in the first case followed by success in the second would isolate caller PATH under this controlled version scenario and support a separately reviewed fix. It would not by itself prove that the deleted D-drive relay had the same root cause. Two failures or two successes do not prove that hypothesis. Even an informative pair does not authorize a tunnel, QA services or Meta changes. `version` is a local CLI query; this harness does not instrument network syscalls or claim a packet-level network audit.

Checks completed during preparation: five pure Node tests (including retained-child STOP/kill and uncertain cleanup with fake children/timers), truthful default plan, PowerShell syntax parsing, and whitespace validation.
