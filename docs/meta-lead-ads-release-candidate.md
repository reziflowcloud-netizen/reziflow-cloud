## First deployment: no activation

Leave every `META_LEAD_ADS_*_ENABLED` switch absent/false, all organization allowlists empty, and all bindings OFF. No bindings, tokens or Meta subscriptions are seeded. Do not populate an App ID or secret just to deploy the disabled code. `META_LEAD_ADS_UI_ENABLED=true` plus an exact server-only `META_LEAD_ADS_UI_ORGANIZATION_IDS` allowlist grants UI/source-option access independently from intake/worker. Owner/Admin and unrestricted access are additionally required for settings. Unapproved organizations receive no integration link or new source options; direct settings and bindings reads/writes return 404. Existing custom source labels/order remain intact. Emergency binding DELETE remains owner/admin authenticated and tenant-scoped after the UI allowlist is withdrawn.

Internal QA Apps, Page and Form are rejected by application configuration/tuple authorization; they cannot be reused as customer configuration. Choose and separately authorize a production Lead Ads app with appropriate external access. Legacy messaging App IDs/secrets cannot be reused. There is no self-service OAuth onboarding in this candidate.

Intake validates the raw HMAC before JSON and exact App/Page/Form/organization binding before receipt insertion. Streaming caps are 64 KiB for webhook, 128 KiB for Graph, 16 KiB for bindings, 4 KiB for retention. Oversize streams are cancelled. Receipts contain identifiers/diagnostic codes and a keyed fingerprint, not contact payloads. Graph defaults to v27.0, supported by the current [Meta guide](https://developers.facebook.com/docs/marketing-api/guides/lead-ads/retrieving/); pin/revalidate the version before external activation.

**OFF is not a queue.** A valid signed webhook while globally disabled is acknowledged 200/disabled without a receipt. Unknown/disabled bindings are rejected without storing contacts. Re-enabling does not backfill the gap. Maintain the existing intake process and an agreed gap ledger before any switch change. Polling/backfill is not implemented or silently enabled.

## Worker and operational alerts

The authenticated POST `/api/internal/meta-lead-ads` requires its own >=32-character worker secret, global intake and worker switches, and a valid app activation timestamp. Each invocation selects at most 20 due receipts and has a 45-second work budget inside the 60-second route limit. Graph has a <=10-second timeout, a 120-second claim lease, eight attempts maximum, and 30-second to one-hour capped backoff for retryable failures. Receipt completion after a lost acknowledgement is recovered from the committed ingestion event. No retry resets are permitted merely to remove an alert.

`scripts/meta-lead-ads-worker.mjs` is a foreground serial scheduler, **OFF by default**. It installs no task, daemon or Vercel cron. It needs a separately approved managed operator host with Node >=22.18, `META_LEAD_ADS_SCHEDULER_ENABLED=true`, `META_LEAD_ADS_WORKER_URL=https://legalhubcrm.com/api/internal/meta-lead-ads`, and the worker secret in private process configuration. Only the canonical origin https://legalhubcrm.com is accepted; alternate/QA hosts, userinfo/query and redirects are refused. Default cadence 60 seconds, configurable within 60–3600; maximum 1440 ticks per run, request deadline 55 seconds, three consecutive failures stop the run with exit code 1. A host supervisor may restart only under the approved operational policy. No scheduler is started by this PR.

Output is JSON with only aggregate counts and fixed alert codes. `severity=alert` on blocked receipts, pending age >300 seconds, or failed request must be wired to an existing operator alert sink **before enabling a tenant**. The responsible operator checks stopped/dead scheduler health independently; silence is not healthy. Keep logs free of URLs, headers, tokens, contact fields and raw Graph errors. Expected response fields are validated and streamed response is capped at16 KiB. SIGINT/SIGTERM aborts the in-flight request and future ticks; global/binding disable is still needed because a remote invocation may already be processing.

## Exact credential attestation / replacement

Perform only under a later named tenant authorization, through a private server-side tool with transport/debug logging disabled. Do not use URLs in browser address bars, shell arguments or screenshots containing credentials. Record only allowlisted technical outcomes in the private attestation, never full Graph responses.

1. Verify the organization's immutable ID, operator authority, dedicated production App identity, intended exact Page and Form. Reject QA resources and any legacy messaging app. Disable the exact binding through its DELETE endpoint first; confirm success/readback. Record the intake gap and preserve the old process. Do not change receipt HMAC key: it defines the dedupe horizon.
2. Obtain/renew only the approved Page-scoped token with minimal approved access; store in the server secret named `META_LEAD_ADS_PAGE_TOKEN_<PAGE_ID>`. No token enters Organization JSON or browser settings.
3. Using the dedicated App's app credential in Authorization, call official `GET /v27.0/debug_token` for that Page token through a secret-safe transport. Require `is_valid=true`, exact `app_id`, correct token type, usable expiry/data-access expiry, the necessary scopes and granular Page scope when returned. An absent/ambiguous Page proof is a blocker, not permission to infer it from a name.
4. With that same Page token, read `GET /v27.0/me?fields=id` and require exact Page ID. Read the Page's `leadgen_forms?fields=id` to prove this exact Form belongs to the Page, following only fixed Graph URL + opaque cursor with a bounded page budget. Failure/exhaustion/ambiguous membership blocks attestation. Verify Lead Access Manager and both App Page-leadgen and Page subscribed_apps entries read-only; metadata access alone does not prove Lead Access. No lead data is needed for this preflight.
5. Compute SHA-256 of the exact token bytes privately. Only after all checks and owner authorization write exactly one server-only approved tuple `{appId,pageId,formId,organizationId,tokenSha256,tokenAppId,tokenPageId,formPageId,verifiedAt}`. Record checkedAt and token-expiry separately in the private operations record. `verifiedAt` must be actual verification time, not renewed by editing a date. Runtime rejects future, >30-day, duplicate, mismatched or changed-fingerprint attestations. Schedule re-verification before the earlier of expiry or day 30; alert at day 25. The attestation is manual evidence, not continuous Graph verification.
6. Configure UI/mode allowlists separately. Create the OFF binding, then activate only after tenant, legal, scheduler, migration and owner gates. Global activation/re-activation requires a new strict UTC ISO timestamp. Confirm aggregate state/readback with no secrets. Old pending receipts before the new activation are blocked, not silently imported.
7. On rejected permission/token/provenance or unverified expiry, keep binding OFF, stop its activation, alert the operator and obtain proper authorization. Do not rotate another app, broaden scope or grant access automatically. Replacing a token invalidates its old fingerprint; repeat all checks before enabling.
